## 2. 안건별 결정사항

### ① 이관 작업 방식
- 현재 구현된 코드(Apps Script 기반)를 그대로 옮길 수 없으므로 **사내 환경에 맞는 이관 작업을 진행한다.**
- 직원용 서비스라 성능 튜닝 부담은 적음 — 그라파나 모니터링·CPU 조정 등의 운영 작업은 거의 없을 것으로 예상.

### ② 쿠버네티스 단일 컨테이너 통합·배포 구조
- **백엔드와 프론트를 단일 도커 컨테이너로 통합해 쿠버네티스(EKS)에 배포**하는 방향 확정.
- **1단계: Apps Script를 대체하는 단일 컨테이너 형태로 코드 구조를 수정하고, 로컬에서 도커 이미지로 실행 가능하도록 작업한다.** (담당: 강원석)
- BE팀에서 쿠버네티스 환경 세트가 돌아가도록 세팅하고 코드 수정·배포 가이드를 제공한다. (담당: 김건우·박현정)
- 배포 체계(BE팀 공유사항): YAML 매니페스트 기반, 사내 깃(GitHub Enterprise)에 소스 푸시 → 신규 도커 이미지를 사내 도커 이미지 저장소에 푸시 → 쿠버네티스 배포. 젠킨스·아르고시디(배포), 그라파나(모니터링) 사용.

### ③ 도메인·서비스 노출
- **사내 도메인 `thinqreal.lge.com`으로 전환한다.**
- 쿠버네티스 배포 후 도메인 연결·사내망 노출 세팅은 박현정 책임(BE팀) 담당.
- 기존 `thinqreal.com`(개인 구매)은 1년 단위 갱신을 유지하지 않는 방향.

### ④ 사용자·관리자 인증
- **사내 SSO(팀즈 기반) 연동을 우선 검토한다.**
- SSO는 공통 플랫폼 영역에서 제공 — 팀즈 로그인 기반 인증 후 **헤더로 사용자 이메일이 넘어오면 관리자 권한 판별은 뒷단 서버에서 처리**한다. (현행 관리자 이메일 명단 판별 로직의 개념 유지)
- 개인정보 영향평가의 SSO 관련 요구사항(MFA 등) 확인 후 설계 확정. (담당: 강원석)

### ⑤ 메일 발송
- **사내 SMTP 서버로 전환한다.** (BE팀: 이미 내부적으로 사용 중이어서 큰 이슈 아님)

### ⑥ 예약 데이터 저장소·구글 캘린더
- **예약 핵심 데이터는 사내 DB(DynamoDB 우선 검토)로 이관한다.** 예약/슬롯/차단 데이터가 정형적이고 날짜 기준 조회·단건 수정·조건부 쓰기 요구와 잘 맞음. 단, 관리자 전체 조회·월간 리포트 집계·날짜/슬롯 중복 예약 제어를 고려한 PK/SK 및 GSI 설계가 선행되어야 함. RDS(MySQL) 대안도 있으나 DynamoDB 예상 — **DB팀과 협의 필요**.
- **구글 캘린더는 API를 통한 동기화용(미러링)으로 유지한다** — 이벤트 등록·삭제만, 데이터 원본 아님.
- 데이터베이스는 업무혁신 산하 DB 인프라 관리팀의 사내 DB를 사용한다.
- **DB 자원 생성 절차 정리 전까지는 구글 스프레드시트 사용을 유지하며 점진적으로 이관한다.** (자원 생성이 가장 까다로운 부분 — 인프라 팀과 협의, 담당: 김건우·박현정)

### ⑦ 메신저 알림·차트 렌더링·정기 스케줄러
- **텔레그램 알림 → MS Teams 워크플로 웹훅으로 전환한다.**
- **월간 리포트 차트는 오픈소스 라이브러리로 서버 내부에서 렌더링한다.** 컨테이너 이미지 안에서 생성 후 즉시 메일에 포함(중간 저장소 없음) — 내부 데이터가 외부 서비스(QuickChart)로 나가는 영향평가 이슈 해소.
- **정기 작업은 Kubernetes CronJob으로 대체한다.**
- **외부 기사 검색 API(Serper)는 현행 유지한다.**

### ⑧ 시스템 확장·타 사이트 대응
- **창원 등 타 사이트는 이 시스템으로 통합하지 않고 사이트별로 별개 운영한다.** — 확대보다 작게 별개 운영이 데이터 정합성 위험을 줄이는 방향.

### ⑨ 사내 AI 코딩 툴 사용 환경 (공유)
- 사내에서 클로드 코드 사용 신청 절차 확인 필요 — 전사 게시판에 관련 내용 있음. (담당: 강원석)

## 4. 미결·추후 검토 항목

- **사내망 노출 경로** — Ingress / 내부 ALB·NLB / 사내 API Gateway 여부, 내부 DNS 연결, 접근 제어 범위 (BE팀, 배포 후)
- **외부 공개 도메인(`thinqreal.com`) 처리** — 유지할지, 사내 전용 도메인으로 전환 후 정리할지. 인증서 발급·DNS 운영 주체를 어느 조직이 맡을지 (추후 검토)
- **DynamoDB PK/SK·GSI 설계** — 관리자 전체 조회, 월간 리포트 집계, 날짜/슬롯 중복 예약 제어 요구 반영 (DB팀 협의와 병행)
- **사내 SMTP 세부** — 발신 주소 정책, HTML 메일 템플릿 호환성, 대량 발송 한도, 운영 계정/인증정보 관리
- **Serper 계약·키 관리** — 서비스 사용 계약, API 키 관리 주체, 장애 시 수동 큐레이션 fallback 운영 방식
- **사내 캘린더 연동 필요 여부** — 구글 캘린더 미러링 유지가 기본이나, 필요하다면 사내 일정 시스템 연동 방안 별도 설계. 없다면 운영 화면 내 예약 조회를 단일 화면으로 단순화 가능

## 5. 1단계 작업 정의 (강원석 담당분)

> 새 이관 전용 세션에서 이 섹션부터 시작하면 된다.

**목표**: Apps Script(`ThinQReal_AppScript.gs`) 전체 기능을 대체하는 백엔드 + 정적 프론트(index.html·thinqreal_admin.html·ThinQ_Real_ROI_Tool.html·images/) 서빙을 **하나의 도커 컨테이너**로 통합하고, **로컬에서 `docker run`으로 기동·검증 가능한 상태**까지 만든다.

**범위 힌트**:
- 엔드포인트 계약은 `api-contract.md` (GET 15종 + POST 9종) — 프론트 3개 HTML의 `SCRIPT_URL` 호출부와 호환되게 구현하면 프론트 수정 최소화
- 데이터 계층은 이관 초기 **구글 스프레드시트 유지(§2-⑥)** — 저장소 어댑터를 인터페이스로 분리해 두면 DynamoDB 전환 시 교체만
- 인증은 현행 HMAC 토큰 구조 유지로 시작(§dependency-inventory: 토큰 형식 유지 시 클라이언트 무변경), SSO 헤더 방식은 요구사항 확인(#4) 후 교체
- 텔레그램→Teams 웹훅, QuickChart→내부 렌더링, 트리거→CronJob 은 1단계 컨테이너 안에서 함께 재구현하거나 스텁으로 두고 순차 전환
- 비밀값(토큰·PW·PIN)은 환경변수로 — 코드·리포에 미기재 (현행 Script Properties 규칙 승계)

**산출물**: Dockerfile + 백엔드 소스 + 로컬 실행 가이드(README) + BE팀 공유용 구조 설명

### 다음 작업에의 함의 (이관 세션용)
1. **2단계 실체 확정**: `server/` 코드를 gitea 저장소의 샘플 자리에 README 규칙대로 이식 → push → ST 자동 배포로 검증하는 흐름.
